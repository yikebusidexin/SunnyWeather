## Context

`bug-autofix-loop` 目前对“已有失败证据（build/test/lint/crash 输出）”的闭环定义较清晰，但对“疑似缺陷/缺陷清单”的输入缺少显式阶段：在没有复现与证据的情况下直接进入修复会导致误修、无法验收、以及沟通成本上升。

本设计将 skill 的入口扩展为两类输入：
- **Bug 清单**：多条缺陷（通常来自测试/用户反馈/issue 列表）
- **自然语言描述**：单条问题描述（可能不包含日志）

并在“修复”前新增 **Triage & Repro** 阶段：逐条给出“是否存在/可复现”的结论、复现步骤与证据收集清单，再进入最小修复与验证闭环。

约束：
- 仍保持 guided 模式：先输出计划，再执行改动
- 默认本地证据优先，网络受限时需可退化（请求离线包/镜像/本地日志）

## Goals / Non-Goals

**Goals:**
- 让 skill 能处理“bug 清单/自然语言描述”输入，并输出标准化的复现流程（环境/步骤/预期/实际/证据）
- 让每个缺陷在进入修复前都有明确的“存在性结论”（可复现/不可复现/证据不足/疑似 flaky/环境问题）
- 将复现流程与验证命令纳入修复方案，便于验收与回归
- 支持批量：对 bug 清单逐条处理，能标记优先级与阻塞项

**Non-Goals:**
- 不要求自动生成完整测试用例（可作为可选建议）
- 不把“产品需求澄清”作为强制流程；仅在预期不明确时提出澄清项

## Decisions

1) **新增 Triage & Repro 阶段作为修复前置**
- 原因：复现是验证与验收的基础；缺陷清单输入时经常缺少可执行证据
- 替代：直接把 bug 清单当作修复任务
  - 取舍：会导致无法确认 bug 是否存在，且修复质量不可控

2) **为每条 bug 输出统一的“结论状态”**
- 状态建议：
  - `reproducible`：可复现（附步骤与证据）
  - `not-reproducible`：按当前信息不可复现（列出缺失信息）
  - `needs-info`：证据不足（明确需要的日志/环境/账号/数据）
  - `flaky-suspected`：疑似不稳定（给出重跑与隔离策略）
  - `environment-blocked`：被环境阻塞（例如 JDK/SDK/网络/权限）
- 原因：让用户知道下一步是什么，避免无限循环

3) **复现输出采用“可复制粘贴”的模板**
- 输出包含：
  - 环境（设备/系统/构建变体/版本号）
  - 步骤（编号）
  - 预期/实际
  - 证据（日志片段/截图/堆栈/失败用例）
  - 最小验证命令（Gradle/测试/lint）
- 原因：便于协作与回归

## Risks / Trade-offs

- **[风险] Bug 清单过长导致响应冗长** → **缓解**：先分组（build/tests/lint/crash/unknown），按优先级/可复现性输出摘要，再逐条展开
- **[风险] 自然语言描述缺少信息** → **缓解**：强制进入 `needs-info` 分支，列出最小缺失信息与获取命令
- **[风险] 将 triage 做成“问答审讯”** → **缓解**：优先给出默认假设与最小证据清单；仅在关键分歧点提问
