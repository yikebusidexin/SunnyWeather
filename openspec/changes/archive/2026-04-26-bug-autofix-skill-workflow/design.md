## Context

本变更的目标不是直接“实现自动修复 bug”，而是建立一个**可复用、可验证、可扩展**的 Cursor 项目级 Skill 工作流，用于在 Android/Gradle 项目中处理常见缺陷：构建失败、测试失败、lint 失败与运行时崩溃。

当前问题的核心在于：修复路径高度依赖个人经验，且缺少统一的闭环（复现 → 诊断 → 最小修复 → 验证）。Skill 的价值在于把该闭环固化成稳定流程，并明确护栏与失败回退行为，避免“盲修复”。

约束与假设：
- Skill 以**项目级**落地（`.cursor/skills/...`），便于在仓库内共享
- 工作方式为 **guided**：先输出诊断与修复方案，再执行代码改动
- 默认不依赖外网；仅当本地证据不足（例如 Gradle/依赖版本兼容问题）时允许查外部资料
- 验证通过是完成标准，至少包含 build/test/lint 中与故障类型匹配的命令

## Goals / Non-Goals

**Goals:**
- 定义 Skill 的触发词、输入输出、以及标准化的“诊断-修复-验证”闭环
- 提供问题分类（build/test/lint/crash）与对应的默认验证命令集合，并留出可配置点
- 规定安全护栏（最小改动、可回滚、避免破坏性操作）与失败回退（证据不足时如何收敛）
- 输出可直接实现为 `.cursor/skills/bug-autofix-loop/`（或等价命名）的一组文件结构与内容要求

**Non-Goals:**
- 不承诺“一键修复所有 bug”；不把复杂重构作为默认路径
- 不引入与项目无关的通用 CI 平台集成（如 GitHub Actions 规则）作为硬依赖
- 不在本设计中规定具体业务逻辑的修复策略（聚焦流程与护栏）

## Decisions

1) **Skill 采用分层流程：证据收集 → 归类 → 最小修复 → 验证 → 循环**
- 原因：缺陷类型差异大，但闭环结构一致；可扩展到更多类别（如格式化、依赖冲突、资源缺失等）
- 备选：针对每类问题写独立 skill
  - 取舍：独立 skill 便于聚焦但难以复用通用步骤；本方案先统一，必要时再拆分

2) **默认 guided 模式（先诊断给方案，再执行改动）**
- 原因：避免在证据不足时直接修改代码造成回归；同时保留自动化效率（执行仍由 agent 完成）
- 备选：完全自动修复（aggressive）
  - 取舍：对仓库安全与可控性要求更高；后续可通过配置扩展

3) **将“完成标准”定义为命令通过，而非“看起来修了”**
- 原因：可验证、可重复；与 CI 逻辑对齐
- 默认命令（Android/Gradle）建议：
  - build：`./gradlew assembleDebug`
  - unit tests：`./gradlew testDebugUnitTest`
  - lint：`./gradlew lintDebug`
  - crash 类：优先补测试/复现步骤；至少保证相关测试与 build 通过
- 可配置点：允许在 skill 文档中列出项目实际命令（或从 README/Gradle task 推断）

4) **护栏默认“最小改动优先 + 可回滚”**
- 原因：bug 修复常见风险是引入新回归；最小改动更容易 review 与定位
- 实施方式：
  - 单次迭代只解决一个失败根因（避免多点同时改动）
  - 对可能破坏性的操作（大版本升级、广泛替换、删除资源）需先给出风险与回退方案

## Risks / Trade-offs

- **[风险] 错误输出不完整导致误判根因** → **缓解**：流程中强制收集“复现命令 + 完整错误段落 + 首个根因栈/首个失败用例”
- **[风险] Flaky 测试导致循环修复无效** → **缓解**：加入“重跑确认/隔离用例/标记不稳定原因”的分支与退出条件
- **[风险] 过度依赖外部资料** → **缓解**：默认本地优先；仅在依赖兼容/工具链报错语义不清时查外网，并在输出中引用证据
- **[权衡] 统一流程可能牺牲特定类别的最佳实践细节** → **缓解**：在 specs 中以“分支规则”补齐每类缺陷的特殊步骤
